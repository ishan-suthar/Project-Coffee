Previously: Brew 53 (date-awareness system prompt) is implemented
on top of Brew 52. The request: Coffee never told any Bean the current
date, so every Bean answered date-sensitive questions ("what's the date
today," "latest," "this week") from its training cutoff - a real example
cited House Blend answering "October 17, 2024" on 2026-07-23. Read
`router/app/main.py` (both orchestration paths), `router/app/history.py`,
`router/app/openrouter_client.py`, and `settings.yaml` before proposing a
plan; confirmed no `system` role appears anywhere in the codebase today
and that `/v1/order` and `/v1/chat/completions` are structurally separate
call paths - `/v1/chat/completions` always sends a caller-assembled
`messages_override` verbatim (Cursor and similar clients send their own
system prompts), `/v1/order` never does - so scoping the injection to
`/v1/order` only falls out of that structure rather than needing a new
flag. New `router/app/system_prompt.py`: `build_date_system_message()`
returns a one-sentence system message ("Today's date is 2026-07-23
(UTC-07:00). Use this as the current date - do not assume a date from
your training data.") or `None` when the new `system_prompt_include_date`
setting (default `true`) is off. Date-only granularity is deliberate -
this rides on every `/v1/order` request, and a per-second timestamp would
defeat prompt caching if that's ever added; a per-day value doesn't. The
UTC offset label (`UTC-07:00`) is used instead of a timezone abbreviation
on purpose - "CST" is genuinely ambiguous (US Central vs. China
Standard). New `system_prompt_timezone` setting (default `"local"`,
resolves the server's own system timezone; set to an IANA name like
`"America/Chicago"` to pin a specific zone) - `tzdata` added to
`requirements.txt` since `zoneinfo` needs it explicitly on Windows.
`router/app/main.py` gained `_with_system_message()`, called once per
`/v1/order` request right after `history_result` is built and reused for
both the draft call and any escalation re-run (so a draft and its
escalation answer the same "today" consistently, even across a pause of
up to `escalation_approval_timeout_seconds`) - it builds a new list
rather than mutating `history_result.messages`, so
`history_turns`/`history_tokens_est`/`message_count`/`total_input_chars`
(all computed from `history_result` before this runs) stay exactly what
they were; the date message is never persisted via
`session_store.add_message`, so it can never become a stored conversation
turn either. **By construction, the system message sits outside the
`history_max_chars` budget** - it's added after history is assembled and
windowed, so at ~130 characters it's never a trimming candidate, but this
also means `history_max_chars` no longer bounds everything sent to
OpenRouter, only the conversation-history portion - noted explicitly so
this isn't misread later as a budget that covers the whole payload. If a
leading system message were ever already present in the assembled
history, `_with_system_message()` merges the date sentence into it rather
than sending two - dead code today (`history.py`'s `pair_turns()`/
`assemble_history()` can only ever produce user/assistant turns) but
exercised directly by a unit test in case that changes. Deliberately
injected on **every** `/v1/order` request regardless of `remember_chat` -
that toggle governs conversation history, not knowledge of the current
date; a user who turns memory off to save tokens still wants correct
dates. This changed the visible shape of `history_messages` sent to
`stream_order_fn` even in the no-history case (a leading system message
instead of `None`), so seven existing tests that used
`history_messages is None` as a proxy for "no history was sent" were
updated to assert the property that actually matters (no user/assistant
roles present) instead - a real improvement on its own terms, not just
churn, since that assertion won't break again the next time something
legitimately rides along in that array. New tests: `test_system_prompt.py`
(message formatting, local vs. pinned IANA timezone, invalid-timezone
fallback, brevity); `test_main.py` additions covering presence/correct
date by default, absence when disabled, non-persistence as a conversation
turn, and - the double-counting check - `history_turns`/
`history_tokens_est`/Ledger `message_count`/`total_input_chars` proven
byte-identical whether the setting is on or off; a `/v1/chat/completions`
test asserting a client's own messages (including one that already leads
